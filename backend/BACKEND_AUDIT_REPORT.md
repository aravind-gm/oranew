## 1. 🔴 Security Issues (CRITICAL)

### SEC-01 ‼️ `.env` file contains ALL production secrets in plaintext
| Severity | File |
|----------|------|
| **CRITICAL** | `.env` |

The `.env` file is committed/accessible and contains **live production credentials**:

| Secret | Exposed Value |
|--------|---------------|
| Database password | `9EtOmJae6YyUxXx2` |
| Supabase anon key | Full JWT |
| Supabase service role key | Full JWT (full admin access to Supabase) |
| Razorpay **LIVE** key ID | `rzp_live_SGNZASNKz1V838` |
| Razorpay **LIVE** key secret | `VSen6fKtVUkAz7AieAfoYWBV` |
| Razorpay webhook secret | `ORAglobal` |
| R2 account ID + keys | All three values |
| Email password | `ORAglobal` |

**Action:** Rotate **every single secret** immediately. Move all secrets to the hosting platform's environment variable system (Render dashboard). Add `.env` to `.gitignore`. Use a secrets manager for local dev.

---

### SEC-02 ‼️ OTP values logged in plaintext
| Severity | File | Lines |
|----------|------|-------|
| **CRITICAL** | `src/controllers/auth.controller.ts` | 453, 663 |

```
console.log(`[Auth] 🔢 Generated OTP for ${email}: ${otp}`)
console.log(`[Auth] 🔢 Generated registration OTP for ${email}: ${otp}`)
```

Any log aggregator, crash reporter (Sentry), or server log viewer exposes customer OTPs, enabling account takeover.

**Action:** Remove OTP value from all log statements. Log only `OTP sent to <email>` with no value.

---

### SEC-03 ‼️ JWT_SECRET fails own production validation
| Severity | File |
|----------|------|
| **CRITICAL** | `.env` + `src/server.ts` |

- `.env` has `JWT_SECRET="ora-jewellery-production-jwt-secret-key-2024-secure"` — only ~50 characters.
- `server.ts` line 62 requires `>= 64` characters in production and will **throw** `FATAL: JWT_SECRET must be at least 64 characters`.
- This means either: (a) the app is not actually running with `NODE_ENV=production`, or (b) the validation was added after deployment and hasn't been enforced yet.

**Action:** Generate a proper secret: `openssl rand -hex 32` (produces 64 hex chars). Set it in Render's environment variables.

---

### SEC-04 ‼️ RAZORPAY_WEBHOOK_SECRET is trivially guessable
| Severity | File |
|----------|------|
| **CRITICAL** | `.env` |

`RAZORPAY_WEBHOOK_SECRET="ORAglobal"` — this is the company name, not a cryptographic secret. An attacker can forge webhook payloads to mark payments as "captured" and steal inventory.

**Action:** Copy the actual signing secret from Razorpay Dashboard → Settings → Webhooks. It should be a random string generated by Razorpay.

---

### SEC-05 Hardcoded email credentials as fallback
| Severity | File | Line |
|----------|------|------|
| **HIGH** | `src/utils/email.ts` | 13–14 |

```ts
user: process.env.EMAIL_USER || 'admin@orashop.in',
pass: process.env.EMAIL_PASS || 'ORAglobal',
```

If the env var is ever unset, the hardcoded password is used. This password is also committed in plaintext.

**Action:** Remove all fallback values. Fail fast if `EMAIL_USER` or `EMAIL_PASS` is missing.

---

### SEC-06 Timing-attack vulnerable signature verification
| Severity | File | Line |
|----------|------|------|
| **HIGH** | `src/utils/payment.ts` | 50 |

```ts
return expectedSignature === razorpaySignature;  // String === comparison
```

The main `payment.controller.ts` correctly uses `crypto.timingSafeEqual()`, but the duplicate utility in `utils/payment.ts` uses `===` which is vulnerable to timing attacks.

**Action:** Use `crypto.timingSafeEqual()` here, or better yet, delete this duplicate file entirely (see DEAD-04).

---

### SEC-07 Extensive password-login debug logging
| Severity | File | Lines |
|----------|------|-------|
| **HIGH** | `src/controllers/auth.controller.ts` | 344–382 |

Logs include:
- `Password length`
- `User found: true/false`
- `Has passwordHash: true/false`
- `User ID`, `User email`
- `Password match result: true/false`

This gives attackers detailed oracle information in logs.

**Action:** Remove all these debug logs. In production, log only "Login succeeded" or "Login failed" without details.

---

### SEC-08 Webhook secret falls back to key secret
| Severity | File | Line |
|----------|------|------|
| **MEDIUM** | `src/controllers/payment.controller.ts` | ~495–500 |

If `RAZORPAY_WEBHOOK_SECRET` is missing, the server returns 500, but the code path around it is fragile. The `utils/payment.ts` duplicate uses `RAZORPAY_KEY_SECRET` as webhook secret — wrong secret for a different purpose.

**Action:** Always require a dedicated webhook secret; fail fast if missing.

---

### SEC-09 Inconsistent bcrypt libraries
| Severity | File |
|----------|------|
| **MEDIUM** | `src/controllers/auth.controller.ts` vs `src/controllers/guestCheckout.controller.ts` |

- `auth.controller.ts` uses `bcrypt` (native C++ bindings)
- `guestCheckout.controller.ts` uses `bcryptjs` (pure JS)

Both are in `package.json`. Using two libraries for the same purpose is a maintenance risk and can cause subtle hash incompatibilities.

**Action:** Standardize on one library (`bcrypt` is faster; `bcryptjs` is more portable). Remove the unused one from `package.json`.

---

### SEC-10 Seed file has hardcoded admin password
| Severity | File |
|----------|------|
| **MEDIUM** | `prisma/seed.js` |

`passwordHash` created from `'admin123'` — if this seed runs against production, it creates an admin account with a trivially guessable password.

**Action:** Use an environment variable for the seed admin password, or ensure seed never runs in production.

---

### SEC-11 JWT_EXPIRES_IN mismatch
| Severity | File |
|----------|------|
| **MEDIUM** | `.env` vs `src/utils/jwt.ts` |

- `.env` sets `JWT_EXPIRES_IN="7d"` (7 days)
- Code default in `jwt.ts` is `"30m"` (30 minutes)

A 7-day access token is excessive; if a token is stolen, the attacker has a week-long window.

**Action:** Use short-lived access tokens (15–30 min) with the refresh token rotation already implemented.

## 2. 🟠 Dead / Unused Code

### DEAD-01 `middleware/supabaseAuth.ts` — completely unused
No route file imports `supabaseAuth`. The main auth system (`middleware/auth.ts`) explicitly reads from cookies only and ignores `Authorization` headers. `supabaseAuth.ts` reads from `Authorization: Bearer` and verifies via Supabase — a completely different auth flow that is dead code.

**Action:** Delete `src/middleware/supabaseAuth.ts`.

---

### DEAD-02 `middleware/rawBody.ts` — replaced by express.raw()
`server.ts` uses `express.raw({ type: 'application/json' })` directly for the webhook path. The manual `rawBody.ts` middleware that attaches `req.rawBody` is not imported anywhere.

**Action:** Delete `src/middleware/rawBody.ts`.

---

### DEAD-03 `middleware/databaseRecovery.ts` — never imported
`databaseRecovery.ts` exports `databaseRecoveryMiddleware` and `withDatabaseRetry`, but neither is imported in `server.ts` or any route. The retry logic in `utils/retry.ts` appears to be the active replacement.

**Action:** Delete `src/middleware/databaseRecovery.ts` or integrate it.

---

### DEAD-04 `utils/payment.ts` — duplicate Razorpay instance
`payment.controller.ts` already creates its own Razorpay singleton. `utils/payment.ts` creates a **second** instance at module load time, and exports functions (`createRazorpayOrder`, `verifyRazorpaySignature`) that duplicate what the controller does. Grep shows no imports of these utility functions from any controller or route.

**Action:** Delete `src/utils/payment.ts` after confirming no imports. Keep `payment.controller.ts` as the single source.

---

### DEAD-05 `codLimiter` — imported but never applied
| File | Line |
|------|------|
| `src/routes/order.routes.ts` | 5 |

`codLimiter` is imported from `rateLimiter.ts` but never used on any route in `order.routes.ts`. Only `checkoutLimiter` is applied.

**Action:** Either apply `codLimiter` to the COD checkout path, or remove the import.

---

### DEAD-06 Unused npm packages

| Package | Reason |
|---------|--------|
| `cloudinary` | Zero imports in any `src/` file. R2 is the storage backend. |
| `@sendgrid/mail` | Zero imports. Nodemailer is used for email. |
| `parse-multipart` (devDep) | Zero imports. Multer handles multipart. |
| `@vercel/node` (devDep) | Backend deploys to Render, not Vercel. |
| `bcryptjs` OR `bcrypt` | One of these is redundant (see SEC-09). |

**Action:** `npm uninstall cloudinary @sendgrid/mail parse-multipart @vercel/node` and remove whichever bcrypt library you don't standardize on.

---

### DEAD-07 `PaymentMethod.STRIPE` enum value — never implemented
`prisma/schema.prisma` defines `STRIPE` in the `PaymentMethod` enum, but there is zero Stripe integration in the codebase. Only `RAZORPAY` and `COD` are used.

**Action:** Remove `STRIPE` from the enum (requires a migration).

---

### DEAD-08 Duplicate `logout` function
Both `auth.controller.ts` and `authToken.controller.ts` export a `logout` function. The route file needs to import one — the other is dead code or a source of confusion.

**Action:** Keep only one `logout` implementation. `authToken.controller.ts` version (which also revokes the refresh token) appears more complete.

## 5. ⚙️ Config Issues

| Module | Location | SMTP Fallback |
|--------|----------|---------------|
| `utils/email.ts` | OTP emails, basic send | `smtp.godaddy.com` |
| `services/email.service.ts` | Order lifecycle emails | `smtp.gmail.com` |

Two separate `nodemailer.createTransport()` calls, two different fallback hosts, two different coding styles. Creates two SMTP connections.

| Module | Location |
|--------|----------|

| `controllers/payment.controller.ts` | Lazy singleton |

---

### CFG-03 File-based CMS — won't work multi-instance
| Route | Storage |
|-------|---------|
| `routes/combo.routes.ts` | `fs.readFileSync` / `fs.writeFileSync` to JSON files |
| `routes/shopall-cms.routes.ts` | `fs.readFileSync` / `fs.writeFileSync` to JSON files |

Render (and any multi-instance or serverless deployment) uses ephemeral filesystems. Written files are lost on redeploy, and different instances have different state.

**Action:** Move CMS config to the database (add a `CmsConfig` model to Prisma schema) or use Redis.

---

### CFG-04 `NODE_ENV="production"` in local `.env`
Developers will hit the 64-char JWT check and crash locally.

**Action:** Align the example with the actual default.

### CFG-06 CORS origins should come from env
Production origins are hardcoded in `server.ts`. If the domain changes or a new subdomain is added, a code change + deploy is needed.

**Action:** Use `CORS_ORIGINS` env var (comma-separated), parsed at runtime.

### CFG-07 `server.ts` logs allowed CORS origins in production
Line ~160: `console.log('[CORS] 🔐 Allowed Origins:', allowedOrigins);`

## 6. 🗄️ Database / Schema Issues

### DB-01 `PaymentMethod.STRIPE` — phantom enum value
The `PaymentMethod` enum includes `STRIPE` but there is zero Stripe code. This misleads developers and could cause invalid data if somehow selected.

**Action:** Remove via migration: `ALTER TYPE "PaymentMethod" DROP VALUE 'STRIPE';` (Postgres ≥ 13).

---

### DB-02 Missing composite index on duplicate order check
`order.controller.ts` runs a query like:
```ts
prisma.order.findFirst({ where: { userId, createdAt: { gte: fiveMinutesAgo } } })
```
Without a composite index on `(userId, createdAt)`, this does a sequential scan on the `Order` table.

**Action:** Add to schema:
```prisma
@@index([userId, createdAt])
```

---

### DB-03 Missing index on `Payment.razorpayOrderId`
The webhook handler looks up payments by `razorpayOrderId`:
```ts
prisma.payment.findFirst({ where: { transactionId: razorpayOrderId } })
```
`transactionId` should have an index for fast webhook processing.

**Action:** Add `@@index([transactionId])` to the `Payment` model.

---

### DB-04 `InventoryLock` cleanup relies on scheduler
Expired `InventoryLock` rows are only cleaned up by the scheduler. If the scheduler fails, locks accumulate and block stock indefinitely.

**Action:** Also add a database-level check or a TTL mechanism.

---

### DB-05 No soft-delete or audit trail on `User`
The `deleteAccount` function in `auth.controller.ts` does `prisma.user.delete()` — a hard delete. For compliance (e-commerce transaction records, GST audit), you may need to retain user data.

**Action:** Consider adding `deletedAt` (soft delete) to the `User` model instead.

## 7. 🚨 Missing Error Handling

### ERR-01 `review.controller.ts` `updateReview` — no input sanitization
`createReview` sanitizes with `DOMPurify`, but `updateReview` does NOT sanitize the `comment` field, allowing XSS if the review comment is rendered in HTML.

**Action:** Apply the same `DOMPurify.sanitize()` in `updateReview`.

---

### ERR-02 Guest checkout — no address limit check
`guestCheckout.controller.ts` creates a new address for each order without checking how many addresses a guest user has. A bot could create thousands of addresses.

**Action:** Add a max address limit (e.g., 10 per user) or reuse existing addresses by matching fields.

---

### ERR-03 `utils/payment.ts` — crashes at module load if env vars missing
```ts
export const razorpay = new Razorpay({ key_id: keyId || '', key_secret: keySecret || '' });
```
Creating a Razorpay instance with empty strings may throw or silently fail at import time, crashing the entire server.

**Action:** Lazy-initialize (which `payment.controller.ts` already does), or delete this file.

---

### ERR-04 No global unhandledRejection handler
`server.ts` has `SIGINT`/`SIGTERM` handlers but no `process.on('unhandledRejection')` handler. An unhandled promise rejection in a scheduler or background job will crash the process.

**Action:** Add:
```ts
process.on('unhandledRejection', (reason) => {
  console.error('[FATAL] Unhandled rejection:', reason);
  Sentry.captureException(reason);
});
```

---

### ERR-05 `services/email.service.ts` — transporter created at import time
The transporter is created at module load. If email env vars are missing, this silently creates a broken transporter that fails on first send with an unhelpful error.

**Action:** Lazy-initialize with validation, matching the pattern in `utils/email.ts`.

---

### ERR-06 No request body size limit on CMS routes
`combo.routes.ts` and `shopall-cms.routes.ts` accept JSON bodies without a size limit (beyond the global `express.json()` default of 100KB). An admin could POST a huge CMS config.

**Action:** Add `express.json({ limit: '50kb' })` specifically on CMS routes.

## 9. ⚡ Performance Issues

### PERF-01 Auth middleware does a DB query on EVERY authenticated request
| File | Line |
|------|------|
| `src/middleware/auth.ts` | ~55 |

```ts
const dbUser = await prisma.user.findUnique({ where: { id: decoded.userId } });
```

Every single authenticated API call results in a `SELECT` on the `User` table to re-verify the role. For a site with moderate traffic, this adds significant latency and DB load.

**Action:** Cache the user role in Redis with a short TTL (e.g., 60s), or include the role in the JWT and only re-verify for admin operations.

---

### PERF-02 File I/O on every CMS request
| Files |
|-------|
| `routes/combo.routes.ts`, `routes/shopall-cms.routes.ts` |

Every `GET` request to CMS endpoints calls `fs.readFileSync()` — a blocking synchronous I/O operation on the main thread. Under load, this blocks the event loop.

**Action:** Move CMS to database + Redis cache, or at minimum use `fs.readFile()` (async) and cache the result in memory.

---

### PERF-03 N+1 potential in abandoned cart scheduler
`utils/scheduler.ts` and `services/jobQueue.service.ts` loop through users with abandoned carts and send emails one at a time. With many abandoned carts, this creates N+1 email sends.

**Action:** Batch email sends or use a queue (BullMQ is already available).

---

### PERF-04 No pagination limit enforcement
Some controllers (e.g., `getOrders`, `getAdminProducts`) accept `limit` from query params. Without a max cap, a client could request `?limit=100000` and pull the entire table.

**Action:** Add `const safeLimit = Math.min(parseInt(limit) || 20, 100);` pattern.

---

### PERF-05 Image processing is synchronous in request cycle
`upload.controller.ts` and `r2-upload.controller.ts` process images (Sharp resize, variant generation) synchronously within the HTTP request handler. For large images, this blocks the response for seconds.

**Action:** Offload image processing to a BullMQ job (the infrastructure is already in place).

---

### PERF-06 `product.controller.ts` — select * on products
`getProducts` fetches full product objects with all fields including long text fields (`description`, `seoMeta`) even when listing. For paginated lists, this transfers unnecessary data.

**Action:** Use `select` to fetch only the fields needed for list views.

---

The `login` function (OTP-based) and `passwordLogin` function share significant boilerplate (user lookup, token generation, cookie setting). Both are exported.

### CQ-04 Inconsistent error response format
Some controllers return:
```json
{ "success": false, "error": "message" }
```
Others return:
```json
{ "success": false, "message": "message" }
```
And the `AppError` class + `errorHandler` middleware use yet another format.

**Action:** Standardize on one response envelope:
```json
{ "success": boolean, "data": any, "error": string | null }
```
